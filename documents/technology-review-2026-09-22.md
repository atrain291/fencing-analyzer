The intended product is clear: an épée coaching system that converts uploaded bout videos into timestamped observations about movement, blade work, distance, timing, technique, and recurring tactical patterns. The longer-term design adds reference comparisons and a practice-feedback loop. For the user's stated priority, existing single-camera footage, I would keep the web application and asynchronous processing architecture, rebuild the measurement pipeline around stable participants and temporal evidence, and evaluate 3D body reconstruction as an optional layer.

The main limitation is not simply the age of YOLOv8. This checkout implements a basic pose-overlay prototype, while much of the ambitious analysis remains in the architecture document. Newer models offer useful options, but tracking correctness, camera geometry, fencing-specific evaluation, and honest treatment of missing observations will determine whether the coaching is trustworthy.

**What the current implementation does**

The FastAPI backend accepts a video, creates a bout, and dispatches a Celery job. The worker probes metadata with FFmpeg, calls Ultralytics tracking with `yolov8n-pose.pt`, stores normalized 2D keypoints in PostgreSQL, and asks Claude for a completion message and general advice. React draws skeletons over the original video.

There is no implemented guard detector, blade tracker, depth model, biomechanical scoring, action classifier, reference comparison, or local Llama inference. The names of those stages and database tables are scaffolding. The actual skeleton has 17 COCO landmarks, despite the architecture document's references to 33. Every stored `z` is explicitly zero; these records are not 3D estimates. See [pose.py](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/pipeline/pose.py#L73) and [video_pipeline.py](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/tasks/video_pipeline.py#L63).

**Code findings that affect results**

1. **High priority: participant identity is discarded.** The worker calls `model.track()` but assigns `kps[0]` to the fencer and `kps[1]` to the opponent on every frame. It never uses track IDs or maps the uploaded profile to a person in the image. If one athlete disappears, the remaining athlete can be relabeled as the other; referees and background fencers are also eligible. I reproduced this by executing the real function with synthetic tracker results: when track 10 disappeared and track 20 remained, track 20 became the fencer. Use a persistent participant-to-track mapping, initial user selection, a piste region, and explicit missing/ambiguous states. Track fragmentation still needs recovery or correction. [pose.py:46](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/pipeline/pose.py#L46)

2. **High priority: saved coaching is omitted from the API response.** The review page reads `data.analysis`, but `BoutRead` declares no such field. I executed the actual Pydantic schema with an object containing analysis and confirmed that serialization removes it. The panel consequently remains at “Loading analysis...” even if analysis exists in the database. Add a typed analysis response and remove the frontend `any` escape. [bout.py:14](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/backend/app/schemas/bout.py#L14), [VideoReview.tsx:89](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/frontend/src/pages/VideoReview.tsx#L89)

3. **The coaching is not bout-specific.** The LLM receives only the number of frames and a duration calculated using a hardcoded 30 FPS. It sees neither images nor joint coordinates. This is an explicit Stage 1 placeholder, not a defect in the language model. Even a video with no detected skeletons can reach the same success prompt. Measure detection coverage first, then supply timestamped events, supported measurements, visibility, and uncertainty to the explanation layer. [llm.py:21](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/pipeline/llm.py#L21)

4. **Overlay timing can make acceptable poses look poor.** Rendering is driven by `timeupdate`, which is not a callback for every displayed frame. Use `requestVideoFrameCallback` and its media timestamp, with a fallback where necessary. The video is letterboxed with `object-contain`, while the canvas fills the entire 16:9 container; other aspect ratios therefore misalign. Compute the actual video display rectangle. The lookup also scans the complete frame list on every update; use a sorted timestamp index and load time windows for longer recordings. [VideoReview.tsx:129](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/frontend/src/pages/VideoReview.tsx#L129), [MDN video frame callback documentation](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

5. **Timing assumes constant frame rate.** `frame_idx / r_frame_rate` does not preserve presentation timestamps for variable-frame-rate inputs. This matters for phone recordings and later timing/velocity measurements. Decode using presentation timestamps, or normalize to a documented constant-rate analysis copy and preserve the mapping to the original video. Track rotation, resizing, and cropping transforms as well. [ingest.py:23](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/pipeline/ingest.py#L23), [pose.py:37](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/pipeline/pose.py#L37), [PyAV timing documentation](https://pyav.basswood-io.com/docs/stable/api/time.html)

**Additional execution issues found by inspection**

These are code/configuration findings, not observations from a running deployment:

- The tracked repository contains Alembic configuration but no revision files. The handoff's `alembic upgrade head` instruction cannot initialize the declared schema on a fresh database by itself. [Alembic environment](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/backend/alembic/env.py#L12)
- The backend declares `Analysis.created_at` as non-null with a Python-side default, while the separate worker model omits the column. With a database created from the backend definition and no external server default, worker inserts will fail. Shared model definitions or consistent server defaults would prevent this drift. [Backend Analysis](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/backend/app/models/analysis.py#L94), [Worker Analysis](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/models/analysis.py#L61)
- A database commit failure leaves the session needing rollback, but the exception handler immediately commits again. It can mask the original error and fail to persist `failed`. Partial frame batches also remain after failure, and rerunning appends duplicates. Introduce analysis-run IDs and explicit retry/idempotency behavior. [video_pipeline.py:95](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/tasks/video_pipeline.py#L95)
- In the supplied Compose configuration, Vite's proxy targets `localhost:8000` from inside the frontend container. The API is a different service; that proxy should use the API service address in this deployment. [docker-compose.yml:11](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/docker-compose.yml#L11), [vite.config.ts:15](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/frontend/vite.config.ts#L15)
- `worker_prefetch_multiplier=1` does not restrict the Celery worker to one execution process. Concurrency is not explicitly limited, so multiple jobs can load independent model copies onto the same GPU. Set an explicit GPU execution policy. [celery_app.py:20](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/worker/app/celery_app.py#L20), [docker-compose.yml:52](https://github.com/atrain291/fencing-analyzer/blob/9ca863f/docker-compose.yml#L52)

**Models and libraries worth evaluating**

These are candidates, not claims of measured superiority on this project's footage. None was benchmarked during this review.

| Need | Candidate | Proposed role and practical limits |
|---|---|---|
| Simple integrated pose/tracking baseline | [Ultralytics YOLO26 pose](https://docs.ultralytics.com/tasks/pose) | Compare a medium model with the existing nano model, after fixing identities. The familiar API reduces migration work. Upgrade the pinned Ultralytics runtime too; a new checkpoint is not compatible merely because its filename is changed. |
| Detailed 2D body and foot landmarks | [RTMPose/RTMW](https://github.com/open-mmlab/mmpose), deployed through [rtmlib](https://github.com/Tau-J/rtmlib) | Run pose on expanded crops of each tracked fencer. Body-with-feet or whole-body models can support foot orientation and extension analysis. rtmlib offers ONNX and other inference backends without the full OpenMMLab dependency stack. More landmarks alone do not guarantee better estimates under masks and gloves. |
| Alternative crop-based pose estimator | [ViTPose/ViTPose++](https://github.com/ViTAE-Transformer/ViTPose) | Include an appropriate checkpoint in an accuracy-focused comparison. Evaluate the weapon wrist, elbow, knees, and feet separately. |
| Interactive athlete selection and video masks | [SAM 3 / SAM 3.1](https://github.com/facebookresearch/sam3) | Prompt with clicks/boxes to select the intended athletes, propagate masks, and assist annotation or correction. It is a segmentation/tracking component, not a skeletal pose estimator. Its current documented runtime requirements exceed the existing PyTorch/CUDA container. |
| Tracking selected visible points | [CoTracker3](https://github.com/facebookresearch/co-tracker) | Experiment with guard/weapon landmarks over short clips and inspect visibility outputs. It tracks pixels, not fencing semantics, and cannot verify a tip absent from the image. The repository reports predominantly CC-BY-NC licensing. |
| Single-image 3D body reconstruction | [SAM 3D Body](https://github.com/facebookresearch/sam-3d-body) | A relevant modern experiment for reconstructing a body mesh and joints from selected frames, including prompt-based correction. Independent frames need temporal association and consistency checks. It does not reconstruct the épée. |
| Video-based 3D human motion | [GVHMR](https://github.com/zju3dv/GVHMR) | Compare short sequences for body orientation and motion coherence. It is a research integration, with body-model and project terms to evaluate, and still requires a shared camera/world frame for two-person distance calculations. |
| Scene depth | [Depth Anything 3](https://github.com/ByteDance-Seed/Depth-Anything-3) | A possible scene-geometry experiment. Metric variants have specific calibration/output conventions. Depth predictions do not establish precise depth for a thin, blurred, or occluded blade. |

My first pose comparison would be the existing YOLOv8 nano baseline, YOLO26 medium, and a crop-based RTMPose/RTMW model. Add ViTPose++ if those leave important errors. Run SAM 3D Body or GVHMR separately on a few difficult exchanges before integrating 3D into the main product. Keep model/version provenance and the original predictions so reprocessing does not destroy comparisons.

**Why Gaussian splatting is not my first investment here**

Gaussian splatting's major contribution is efficient scene representation and novel-view rendering. The original method starts from calibrated views and sparse reconstruction points. Dynamic and learned single-view variants broaden what is possible, but creating a convincing unseen view does not establish the true hidden joint or weapon position. A moving fencer filmed by a fixed camera also changes pose between frames, so those frames are not ordinary multiview observations of an unchanged object. [Original Gaussian splatting project](https://repo-sam.inria.fr/fungraph/3d-gaussian-splatting/)

For this application, I infer that body-motion recovery, participant tracking, and piste calibration have a more direct path to useful coaching. Gaussian rendering could eventually be a presentation layer for reconstructed motion. It should not be treated as evidence that centimeter-level blade geometry has been recovered.

SAM 3D Body and video human-motion models are closer to the reconstruction capability the user is looking for. Their outputs still require validation on fencing. In particular, do not subtract two independently reconstructed, body-relative poses and label the result as the distance between the athletes.

**The blade and physics design needs an observational foundation**

The original document proposes deriving a blade axis from wrist and guard centers, projecting a nominal blade length, then correcting flex from acceleration. This is a useful prior to investigate, but those observations do not uniquely determine blade orientation, grip articulation, depth, flex, contact forces, or initial blade state. Small errors in the short wrist-to-guard vector can become large errors when extrapolated to the tip. A physical simulator can generate a consistent solution without showing that it is the actual motion.

I would first label and detect the guard, visible blade segments, and visible tip in high-resolution crops. Combine those observations with temporal tracking and geometric constraints. Mark each output as observed, inferred, or unavailable; terminate extrapolation when evidence becomes insufficient. Use physics to constrain candidate trajectories once those measurements exist. Do not let a simulated hidden tip drive a precise “missed by X centimeters” explanation.

Likewise, launch readiness, weight distribution, target probability, correction cost, and effective-distance penalties in the specification are proposed constructs. They need operational definitions and validation against labeled events and outcomes. A formula does not become a calibrated probability merely by normalizing it to 0–1. Pose alone does not measure the ground forces needed to establish actual weight distribution. Start with visible movement and timing descriptors that a coach can inspect.

**A stronger pipeline for existing single-camera footage**

1. Decode with presentation timestamps; detect cuts, replays, changes in viewpoint, and inadequate visibility.
2. Let the user select the athlete and opponent once, with a simple correction flow if tracking breaks. Map them to persistent participant IDs within each shot.
3. Detect/track the people, then estimate pose in their crops. Preserve confidence, missing values, and crop-to-video transforms. Evaluate temporal smoothing for both noise reduction and unwanted timing shifts.
4. Use visible piste geometry to estimate ground-plane movement and spacing where calibration is adequate. A ground-plane homography applies to points on that plane; it does not directly provide wrist or tip height/depth. Update calibration when the camera moves or zooms. [OpenCV homography explanation](https://docs.opencv.org/4.5.1/d9/dab/tutorial_homography.html)
5. Segment exchanges and infer actions using sequences of both participants' motion plus the original video. Pose is useful, but discarding the pixels also discards weapon and context evidence. Start with a small, reviewable vocabulary and allow uncertain labels.
6. Produce timestamped observations such as extension order, footwork sequence, recovery duration, and spacing trend, qualified by visibility and viewpoint. Use scoring lights/OCR where visible as a separate outcome signal; their timing is not automatically the exact contact instant.
7. Let a language model explain the supported observations, link them to clips, and distinguish measurement from interpretation. Optional 3D visualization should retain those same uncertainty labels.

For an API-based option, Gemini supports direct video input and is worth comparing for broad exchange summaries or candidate event labels. Its default static processing samples at 1 FPS, with other processing modes and controls available. Default sampling can miss fast fencing events; even denser sampling does not establish calibrated joint/weapon measurements. My recommendation is to use a video language model for semantic assistance and explanations, with explicit evidence for precise claims. [Gemini video documentation](https://ai.google.dev/gemini-api/docs/video-understanding)

**Research especially close to this project**

[VirtualFencer](https://arxiv.org/html/2507.00261v1) extracts fencing motion and strategy from existing videos. Its pipeline uses WHAM for body reconstruction, SAM2 for masks, and piste-line geometry to correct global athlete positions. The authors report that unmodified WHAM supplied useful local poses but insufficiently accurate global translation for fencing. That is unusually relevant evidence for adding sport-specific geometry. Its strategic model uses priority-related context and should not be transferred wholesale to this épée coaching product; its evaluation is also not a validation of precise blade tracking.

[FACTS](https://arxiv.org/abs/2412.16454) studies action recognition from raw fencing video and reports an eight-action dataset. It is a useful source to inspect for an action-classification baseline, after checking weapon type, label definitions, access, and data splits. Its reported classification result is not an expected accuracy for this application.

[FERA](https://arxiv.org/abs/2509.18527) is a foil decision-support study whose architecture separates participant tracking, temporal perception, structured decision logic, and explanations. That separation is useful here even though its rules and decision task differ.

**The next experiment I recommend**

Build a small evaluation set before rewriting the application: approximately 20 representative short clips, with clear and difficult cases, both handednesses, camera motion, overlap, blur, and background people. Label participant identity, selected visible joints, visibility, and a small set of action boundaries. Include dense annotations around a few exchanges so timing and jitter can actually be evaluated. Split by bout/source, not by adjacent frames, to avoid misleading results if fine-tuning is introduced.

Compare the three initial pose pipelines on identity switches, visible-joint error, missed-joint coverage, weapon-side left/right mistakes, temporal jitter, event-boundary timing, runtime, and GPU memory. Keep unobservable landmarks unknown in the labels. For 3D, 2D reprojection and plausible motion are useful checks but do not prove depth accuracy; reference 3D capture would be needed to quantify that separately.

Choose the pipeline based on these clips, then add the first few coaching observations and have them checked by a fencing coach. Useful, inspectable timing and footwork feedback can arrive before reliable blade reconstruction. This is a bounded experiment with a clear decision at the end, rather than a commitment to a large reconstruction stack.
